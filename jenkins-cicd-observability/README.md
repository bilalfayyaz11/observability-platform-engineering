# Jenkins CI/CD Observability Platform

## What This Does

This implementation provides an end-to-end observability architecture for Jenkins-based software delivery.

Jenkins build and pipeline telemetry is collected by Prometheus alongside Linux host metrics and custom deployment metrics. Prometheus evaluates CI/CD-specific alert rules, forwards firing alerts to Alertmanager, and Alertmanager routes notifications to a persistent webhook receiver.

The environment includes deterministic successful and failed Jenkins executions, controlled Jenkins outages, stateful deployment telemetry, automated alert validation, and evidence showing that the complete monitoring and notification path operates correctly.

Rather than depending on hard-coded metric names from older Jenkins integrations, the implementation inspects the actual metric families exposed by the installed Jenkins Prometheus plugin and builds monitoring logic around telemetry that really exists.

This provides a reproducible foundation for monitoring CI/CD infrastructure in DevOps, SRE, Platform Engineering, AIOps, and production delivery environments.

## Jenkins Metrics Integration

Jenkins exposes Prometheus-compatible telemetry at:

    http://127.0.0.1:8080/prometheus/

Prometheus scrapes the endpoint using:

    job_name: jenkins
    metrics_path: /prometheus/


The integration is validated through:

    up{job="jenkins"}

Expected healthy value:

    1


## Metric Discovery

Jenkins Prometheus plugin metric names can change across plugin generations.

Instead of assuming historical metric names, this implementation captures the actual exposition and builds an inventory of metric families.

This allows alert logic to be derived from telemetry the installed Jenkins controller really publishes.

The workflow is:

    Jenkins /prometheus/
          ↓
    collect exposition
          ↓
    extract metric families
          ↓
    identify build / queue / executor metrics
          ↓
    generate compatible alert rules


## Jenkins Build Simulation

### Deterministic Build Outcomes

The sample Jenkins job exposes:

    FORCE_FAIL=false

for successful builds and:

    FORCE_FAIL=true

for controlled failures.

This avoids random failure behavior and makes monitoring validation reproducible.


### Build Evidence

The execution history contains both:

    SUCCESS
    FAILURE

results.

Build duration and result information is also collected from the Jenkins API.


## Long-Running Execution

A configurable Jenkins workload accepts:

    DURATION_SECONDS

This makes duration testing repeatable without hard-coding a long sleep into the job definition.

The execution can therefore be reused for different duration thresholds.

## Deployment Metrics

The custom exporter maintains state rather than generating random counter values during every Prometheus scrape.

### Counters

    cicd_deployments_total{result="success"}

    cicd_deployments_total{result="failure"}


These counters increment only when deployment events occur.


### Success Ratio

    cicd_deployment_success_ratio


The value uses the conventional ratio:

    0.0 → 1.0


For example:

    0.90 = 90 percent


### Deployment Duration

    cicd_last_deployment_duration_seconds


This tracks the duration associated with the latest simulated deployment.


## Why Stateful Metrics Matter

Prometheus counters are expected to increase monotonically during a process lifetime.

An implementation that generates a random value for a counter during every scrape can produce:

    500
    172
    843
    301

which violates counter semantics.

The implementation here instead performs:

    deployment event
         ↓
    increment counter
         ↓
    update gauges
         ↓
    expose stable state
         ↓
    Prometheus scrape


This produces valid time-series behavior.


## Jenkins Alerting

The guaranteed Jenkins availability alert uses:

    up{job="jenkins"} == 0


This is independent of Jenkins plugin metric naming because the `up` metric is generated by Prometheus.


Additional Jenkins alerts are generated only when compatible metric families actually exist in the installed Jenkins exposition.


## Deployment Alerts

### Low Deployment Success Ratio

Expression:

    cicd_deployment_success_ratio < 0.90


This detects a success rate below 90 percent.


### High Deployment Duration

Expression:

    cicd_last_deployment_duration_seconds > 1.5


This detects an unusually slow deployment execution.

## Prometheus Configuration Reload

Prometheus runs with:

    --web.enable-lifecycle


Configuration changes are applied through:

    POST /-/reload


The Prometheus PID is captured before and after reload.

Matching process IDs prove configuration changes occurred without restarting the Prometheus process.

## Security Controls

The environment uses several basic hardening practices.

### Localhost Binding

Internal services are bound to localhost where external access is unnecessary.

This includes:

    Jenkins
    Prometheus
    Node Exporter
    Alertmanager
    webhook receiver
    deployment exporter


### Dedicated Service Accounts

Prometheus-related services use restricted service accounts where appropriate.


### Binary Ownership

Downloaded application binaries remain owned by:

    root:root


Writable runtime and data paths are owned by their service accounts.


### Jenkins Credentials

The generated Jenkins administrator password is stored outside the implementation workspace.

Temporary CLI authentication files are deleted after use.

Credential leakage checks verify that the administrator password does not exist inside the repository-ready workspace.

## Real-World Use Case

CI/CD infrastructure is production infrastructure.

If Jenkins or another delivery controller becomes unavailable, software delivery can stop even when the deployed application itself remains healthy.

Observability therefore needs to cover more than application runtime.

Teams need visibility into:

    controller availability
    build failures
    build durations
    executor pressure
    queue pressure
    pipeline outcomes
    deployment success rates
    deployment latency
    underlying host resources


An integrated Prometheus architecture provides a common telemetry and alerting layer for these signals.

## Lessons Learned

- CI/CD controllers should be monitored as production infrastructure.
- Jenkins plugin metric names should be discovered from the live exposition rather than assumed from old examples.
- Prometheus counters must represent monotonically increasing event totals.
- Deterministic failure injection is more useful for validation than random failures.
- Successful and failed CI/CD executions should both be represented in monitoring evidence.
- Prometheus target health can verify the monitoring path independently of Jenkins-specific metrics.
- `up{job="jenkins"}` provides a stable availability signal regardless of plugin metric changes.
- Alertmanager routing should be validated independently before testing Prometheus-generated alerts.
- Persistent webhook services are preferable to unmanaged background processes.
- Localhost binding reduces unnecessary service exposure in single-host architectures.
- Configuration should be validated before lifecycle reload.
- Process IDs can prove Prometheus reloaded without restarting.
- CI/CD observability should combine pipeline telemetry with host telemetry.
- Monitoring implementations are stronger when they preserve evidence of failure, alerting, and recovery.
