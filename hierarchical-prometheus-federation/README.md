# Hierarchical Prometheus Federation

## What This Does

This implementation builds a hierarchical Prometheus monitoring architecture consisting of two independent cluster-level Prometheus instances and one global federation instance.

Each cluster-level instance owns its own local scrape cycle and collects host and application telemetry. The global Prometheus layer selectively retrieves only the metrics required for cross-cluster visibility through the native `/federate` endpoint.

External labels preserve the identity and region of every originating cluster, while recording rules provide stable pre-computed aggregates for global dashboards and alerting systems. Synthetic application telemetry is included to validate request rates, latency percentiles, label preservation, and cardinality behavior across the full federation path.

## Cluster-Level Prometheus

Each cluster-level instance collects:

- its own Prometheus process metrics
- local Node Exporter metrics
- synthetic application telemetry

Cluster A assigns:

    cluster: cluster-a
    region: us-east-1

Cluster B assigns:

    cluster: cluster-b
    region: us-west-2

These external labels remain attached when metrics cross the federation boundary.


## Global Federation

The global instance does not scrape application or infrastructure exporters directly.

Instead, it retrieves a restricted metric subset from:

    http://127.0.0.1:9090/federate
    http://127.0.0.1:9091/federate

Federation jobs use:

    honor_labels: true

This preserves the original cluster and region labels instead of replacing them with labels generated by the global scrape job.


## Selective Federation

Only metrics required for global analysis are federated.

Examples include:

    up
    node_cpu_seconds_total
    node_memory_MemAvailable_bytes
    node_filesystem_avail_bytes
    app_http_requests_total
    app_request_duration_seconds_bucket
    app_request_duration_seconds_sum
    app_request_duration_seconds_count

Keeping the selector narrow limits unnecessary global time-series growth.


## Recording Rules

The global instance defines pre-computed cross-cluster signals.

### Cluster CPU Utilisation

    cluster:node_cpu_utilisation:avg1m

Expression:

    1 - avg by (cluster) (
      rate(node_cpu_seconds_total{mode="idle"}[1m])
    )

This produces one CPU utilisation series per cluster.


### Cluster Available Memory

    cluster:node_memory_available_bytes:avg

Expression:

    avg by (cluster) (
      node_memory_MemAvailable_bytes
    )


### Global CPU Utilisation

    global:node_cpu_utilisation:avg1m

Expression:

    avg(cluster:node_cpu_utilisation:avg1m)

The cluster dimension is intentionally removed to create one global signal.


## Federation Health Alert

The global rules include:

    FederationTargetDown

Expression:

    up{job=~"federate-.*"} == 0

The alert enters a firing state when a federation target remains unavailable for more than two minutes.

The alert carries:

    severity="critical"

and includes the failed instance in its annotations.


## Synthetic Application Telemetry

Two Python-based traffic exporters simulate application activity independently.

Cluster A:

    127.0.0.1:8080

Cluster B:

    127.0.0.1:8081

Each exporter exposes:

### Request Counter

    app_http_requests_total

Labels:

- method
- status_code
- endpoint


### Request Duration Histogram

    app_request_duration_seconds

Buckets:

    0.05
    0.1
    0.25
    0.5
    1.0
    2.5


### Active Sessions Gauge

    app_active_sessions

Active sessions fluctuate within a bounded range to create realistic metric variance.


## Python Dependency Isolation

The synthetic exporter runs from:

    /opt/prometheus-federation/venv

This keeps the `prometheus_client` dependency isolated from Ubuntu's system Python environment.


## End-to-End Queries

### Request Rate Per Cluster

    sum by (cluster) (
      rate(app_http_requests_total[2m])
    )

Expected result:

- cluster-a
- cluster-b

Both should report non-zero rates.


### P95 Request Latency Per Cluster

    histogram_quantile(
      0.95,
      sum by (cluster, le) (
        rate(app_request_duration_seconds_bucket[2m])
      )
    )

This validates histogram aggregation across the federation boundary.


### Label Preservation

Query:

    app_http_requests_total

Every returned series should include either:

    cluster="cluster-a"

or:

    cluster="cluster-b"


## Cardinality Budget

The global Prometheus instance is expected to remain below:

    2000 active series

The global process metric:

    prometheus_tsdb_head_series

is inspected directly from the global instance's own `/metrics` endpoint.

This avoids confusing the global TSDB count with similarly named metrics federated from upstream Prometheus instances.


## How to Reproduce

Validate all configurations:

    promtool check config /etc/prometheus/cluster-a/prometheus.yml

    promtool check config /etc/prometheus/cluster-b/prometheus.yml

    promtool check config /etc/prometheus/federation/prometheus.yml

    promtool check rules /etc/prometheus/federation/rules.yml


Start all services:

    sudo systemctl enable --now node-exporter-a
    sudo systemctl enable --now node-exporter-b
    sudo systemctl enable --now prometheus-a
    sudo systemctl enable --now prometheus-b
    sudo systemctl enable --now prometheus-federation
    sudo systemctl enable --now traffic-simulator-a
    sudo systemctl enable --now traffic-simulator-b


Verify service state:

    systemctl is-active node-exporter-a
    systemctl is-active node-exporter-b
    systemctl is-active prometheus-a
    systemctl is-active prometheus-b
    systemctl is-active prometheus-federation
    systemctl is-active traffic-simulator-a
    systemctl is-active traffic-simulator-b

## Real-World Use Case

Large organizations often operate independent Prometheus instances across regions, environments, or Kubernetes clusters.

Sending every metric to a single global Prometheus instance can create scaling, reliability, and cardinality problems. Hierarchical federation allows local monitoring systems to retain detailed telemetry while forwarding only strategically important signals to a global layer.

This architecture is useful for:

- multi-region infrastructure
- multiple Kubernetes clusters
- platform engineering
- centralized SRE operations
- global reliability dashboards
- cross-cluster anomaly detection
- capacity analysis
- executive service-health reporting


## Lessons Learned

- Prometheus federation is most effective when upstream instances retain ownership of detailed local telemetry.
- External labels provide essential provenance for metrics crossing monitoring boundaries.
- `honor_labels` determines whether original upstream identity survives federation.
- Global metric selectors should remain intentionally narrow to prevent cardinality growth.
- Recording rules reduce repeated query computation and create stable downstream interfaces.
- Prometheus histograms are represented through `_bucket`, `_sum`, and `_count` series and those generated series must be available for percentile calculations.
- Synthetic application telemetry is useful for proving an observability pipeline before integrating real workloads.
- Global cardinality should be measured against the global Prometheus instance itself rather than assuming a federated metric with the same name represents local state.


## Troubleshooting Log

### Outdated Prometheus Version

The original implementation guidance referenced an older Prometheus release.

A current Prometheus 3.x binary was installed from the official release artifacts instead.


### Outdated Node Exporter Version

The original Node Exporter version was replaced with a current release.


### Prometheus Console Assets

Modern Prometheus packages may not contain the legacy console directories expected by older systemd examples.

The installation checks for those assets rather than assuming they exist.


### Public Monitoring Listeners

All monitoring processes run on the same host.

Services were therefore bound to:

    127.0.0.1

instead of exposing operational monitoring ports on all interfaces.


### Python Package Management

Ubuntu's system Python environment is externally managed.

The synthetic exporter uses a dedicated virtual environment rather than installing application dependencies globally.


### Histogram Federation

Percentile calculations require histogram bucket series.

The federation configuration therefore explicitly includes:

    app_request_duration_seconds_bucket
    app_request_duration_seconds_sum
    app_request_duration_seconds_count


### Cardinality Validation

The metric:

    prometheus_tsdb_head_series

also exists on upstream Prometheus instances.

Because that metric can itself be federated, using an unrestricted global PromQL query may return upstream values.

The global instance's own `/metrics` endpoint is used when enforcing the global cardinality budget.


### Federation Label Collision

The global instance uses:

    honor_labels: true

so source cluster labels survive federation and do not get replaced by the global federation job's scrape labels.
